# Hardening the identification rules

Status: proposal, not started. Nothing below has been implemented. The rules as
they stand are written down in [docs/identification_rules.md](../docs/identification_rules.md)
and the counts quoted here are regenerated by `tools/audit_identification_rules.py`
into [docs/paper/data/identification/](../docs/paper/data/identification/).

## Goal

Four things are true of the identification rules today, and each is a separate
kind of failure:

1. **Charge, multimer, adduct and isotope hypotheses are recorded and then
   ignored.** The delivered ladder names 489 distinct ions and stores a neutral
   mass for each, and 99.7% of those masses are the plain `[M±H]` value whatever
   ion the label names.
2. **Isotope and halogen evidence exists in committed data and nothing reads
   it.** 2,115 of 4,483 features carry isotope element hints; 20 features carry
   direct chlorine or bromine evidence. The rules that would consume it are
   implemented and correct, and their only input path is an HTML report bundle
   the shipped pipeline never produces.
3. **One halogen rule is inverted by a typo-class bug.** Every chlorinated and
   brominated MS2 fragment formula is discarded on every feature.
4. **Several standard formula checks are absent**, and their absence is not
   recorded anywhere a reader of the output would find it.

The goal is to close 1 through 3 and to decide 4 on measurement. Not to make the
pipeline more permissive: every stage here narrows what can be claimed as much as
it widens what can be matched, and the gates exist to keep that honest.

## What this does not plan

**Mass tolerance.** Four windows are in force and they disagree by three orders
of magnitude, but that is measured and owned by
[plans/mass_policy_impact_measurement.plan.md](mass_policy_impact_measurement.plan.md)
and [docs/mass_axis_decisions_needed.md](../docs/mass_axis_decisions_needed.md).
Do not re-open it here; stage 1 changes *which mass a candidate is compared
against*, not *how close it has to be*.

**The mass gate at rank 1.** Item 2 of
[docs/pipeline_refinement_handoff.md](../docs/pipeline_refinement_handoff.md),
with a working prototype. Orthogonal, and it will interact: stage 1 changes which
candidates are mass-consistent, so run the gate's prototype again afterwards
rather than trusting its current 523-recoverable figure.

**Re-deriving the reference tables.** FML-1 through FML-5 live in fetched
pickles. They cannot be rebuilt or verified in this checkout.

**Deciding which ion a feature actually is.** This plan makes the arithmetic
follow the label. It does not ask whether the label is right.
[plans/ion_identity.plan.md](ion_identity.plan.md) owns that question — clustering
the co-eluting ion forms recorded in `consensus_observed_adducts`, scoring each
adduct hypothesis against the observed MS2, and reporting the winner as
"compound, observed as [adduct]". The two plans share
`structural_elucidation/chemistry/adducts.py` from stage 0 below, which must have
exactly one implementation of the grammar and the inversion.

The seam matters for stage 1 specifically. If the ladder's ammonium labels name a
co-observed buddy peak rather than the feature's own ion, then deriving a neutral
mass from the label makes those rows *worse*, not better — see the first unresolved
question in the ion-identity plan, which has the measurement that would settle it.
Treat the 66 NH-bearing rows in lib400 and lib402 as blocked on that answer rather
than as ordinary members of the `adduct_or_cluster` family.

## Key decisions already taken

Taken so the next agent does not relitigate them. Reverse any of them
deliberately, not by accident.

- **Repair at load, not in the data file.** `data/feature_rows/*_neutral_mass_hypotheses.csv`
  is an upstream CHRO_LIB export (`source_reference = chrolib_observed_adduct_ladder`)
  and its producer is not in this repository. Editing the committed CSV would
  make the next export silently regress. The repair belongs in
  `pipeline/candidates.py`, marked and flagged, with the upstream fix filed
  separately.
- **The label is the authority, the columns are the fallback.** `charge` and
  `multiplier` agree with the ion named in the label on all 5,988 rows where both
  are populated, so they are not an independent source. Parse the label; fall back
  to the columns only when it does not parse.
- **One implementation of the arithmetic.** The forward equation and its inverse
  go in the package and are imported by the tool, following the precedent of
  `structural_elucidation/inference/mass_windows.py`, which exists precisely so
  the documentation and the scorer cannot drift apart.
- **Unparseable labels stay unparsed.** 45 rows use an uppercase `M+21`
  convention that is not the lowercase ion grammar. Guessing at them invents data;
  count them and leave them on the fallback mass.
- **Nothing widens ranking before it is measured.** Every stage that changes a
  neutral mass ships behind a flag, with the affected-row count reported first.

## Constraints

- **No report bundle in this checkout.** Stages 1, 2 and 3 can be *built* and
  unit-tested here; their effect on delivered results can only be measured where a
  bundle exists (see `docs/ec2_export_handoff.md`).
- **The vendored NCE stack does not run here.** Stage 4 is a code fix with a
  contract test, not a verified behaviour change.
- **Any change that moves the mass axis invalidates the Platt calibration**
  (`PLATT_A`, `PLATT_B` in `reports/confidence.py`, refit by
  `tools/calibrate_confidence.py`) and every audited number in `docs/paper/`. Stage
  1 moves it. Budget the refit and the re-audit into stage 1, not after it.
- **CI runs a regenerate-and-diff.** Anything written under `docs/paper/data/`
  must reproduce byte-identically from committed inputs
  (`.github/workflows/publication-checks.yml`).
- **Compliance.** Observed MS2 ion detail is internal-only. Stage 6 adds a report
  line; keep it to element constraints, not fragment m/z.

Pure refactor. No behaviour change, so nothing gates on it, but stages 1 to 3 all
need it.

Create `structural_elucidation/chemistry/adducts.py` holding what
`tools/audit_identification_rules.py` currently has: the isotope delta and
element mass tables, `parse_adduct_label`, the `Adduct` value object,
`neutral_mass_from_adduct`, `naive_neutral_mass`, `label_family`,
`is_derivationless_label`, and `merge_element_hints`. Have the tool import them
and delete its copies. Move `tests/test_identification_rules.py`'s grammar and
arithmetic tests onto the package module; leave the end-to-end tests on the tool.

The module must stay standard-library only below the numpy line — the tool is in
the CI documentation job, which does not install the inference stack.

**Expected output:** identical audit JSON, byte for byte. That is the test.

## Stage 1 — a hypothesis that follows the ion it names

The core change. `pipeline/candidates.py::mass_hypotheses` (around line 307)
currently takes `target_neutral_mass` straight from the CSV's `neutral_mass`
column. Replace with: parse `adduct_label`; if it parses, derive the neutral mass
from `parent_mz` under the forward equation; otherwise keep the stored value.

Emit alongside it, per row, so the change is auditable rather than invisible:

- `neutral_mass_source` — `label` / `stored` / `charge_columns`
- `neutral_mass_stored` — what the CSV said
- `neutral_mass_shift_da` — the difference

Ship it behind `--derive-neutral-mass-from-adduct` (default **off** for the first
run) so the two can be compared on one input.

**The gate.** Before turning it on, report: how many of the 10,568 hypotheses
move by more than the mass tolerance, how many distinct controls that touches, and
how many candidate rows change mass-consistency class as a result. From the audit
the first number is expected to be about 4,100 (the isotopologue, multimer,
multiply-charged, adduct and numeric-offset families), which is large enough that
the effect must be measured and not assumed benign.

**The risk to measure, not argue.** A correct wider target set finds structures a
`[M±H]`-only set cannot. It also admits candidates at masses that were previously
unreachable, and the mass axis is 0.30 of the confidence score. Measure paired, on
the truth controls, the way `tools/audit_mass_policy.py --rerank` already does it:
same candidates, both policies, exact McNemar on rank-1 and rank-3.

**Verification:** unit tests on the derivation per ion family; a regression test
that `protonated` rows are unchanged to 1e-9 Da (they are already right, and a
refactor that moves them is a bug); the paired comparison above.

## Stage 2 — charge state cannot be assumed

Two parts, and the second is worth shipping even if the first slips.

**2a. Fallback to the declared columns.** When a label does not parse but `charge`
and `multiplier` are populated, derive the neutral mass from those: `M = (z*mz +
s*z*m_e + z*proton_equivalents) / n`. Covers the rows stage 1 leaves behind.

**2b. An invariant, not a score.** No candidate may hold MSI Level 1 or 2 while its
exact mass is a near-exact integer multiple or reciprocal of the observed neutral
mass. `charge_state_suspects` in `tools/audit_mass_policy.py` already implements
the detector at a relative tolerance of 1e-4; lift it into
`reports/confidence.py` as a cap, in the same place the refuting-curation cap sits.

This is worth doing on its own because the failure it catches is not a scoring
error. `X-21470` is a disulfate read as singly charged: MSI Level 1, Confirmed
tier, a `mass_match_score` of 0.95 recorded against a 233 Da error, and nothing
flagged it. Five such reports exist among the 2,471 carrying both masses. A cap
costs nothing on the other 2,466.

**Verification:** `charge_state_suspects` reports zero after stage 1; a unit test
that a fabricated 2.0000x candidate cannot reach Level 2; no report at Level 1
carrying an unexplained integer mass ratio.

## Stage 3 — feed the isotope and halogen rules

The rules (ISO-4 through ISO-7) are implemented and correct. They are starved:
their only producer, `parse_html_signals`, reads a per-feature NCE elucidation
HTML page, and `run_inference.sh` never passes `--isotope-signals-csv` to the pool
stage, so every candidate takes the 0.5 uninformative prior and the
`formula_impossible` filter drops nothing.

Write `tools/build_isotope_signals.py`: read the committed feature rows, merge
isotope tokens from `adduct_label` and from the consensus `note`
(`merge_element_hints` from stage 0), and emit the columns
`pool_v1.join_isotope_signals` already reads — `control_id`,
`canonical_2d_smiles`, `isotope_formula_score`, `isotope_ratio_score`,
`isotope_audit_status`, `isotope_signal_count`. Then pass `--isotope-signals-csv`
from `run_inference.sh`.

**Scope limit, state it in the output.** The ladder carries element hints and no
intensities. `adduct_score` is a per-adduct-type confidence (0.97 for `m-H`, 0.88
for an isotopologue, 0.78 for a numeric offset), not a measured isotope ratio. So
this feeds ISO-4 (`isotope_formula_score`) and ISO-6, and **cannot** feed ISO-5
(`isotope_ratio_score`), which must stay at its 0.5 prior until real MS1
intensities are propagated. Do not synthesise a ratio from `adduct_score`.

**What it buys.** Element hints for 47% of features, and the pipeline's only
chlorine and bromine evidence: 18 features hinting Cl, 5 hinting Br, across 19
controls. `formula_impossible` becomes reachable, which means a candidate whose
formula has no chlorine can finally be dropped from a feature whose spectrum shows
a 37Cl peak.

**Decision needed before writing the producer.** ISO-4 is a floor (`count >= k`)
while the NCE rule ISO-3 is a two-sided window (`|Cl - Ĉl| <= 0.5`). Under the
floor, a formula with four chlorines satisfies a one-chlorine hint, which is wrong
for chlorine: the 37Cl envelope constrains the count from above as well. Recommend
matching ISO-3 for Cl and Br specifically and leaving carbon as a floor, since the
carbon hint from a ladder label is a lower bound on what was observed rather than
a count.

**Verification:** the producer's output validates against the pool's reader; a
control with a known chlorinated truth structure keeps it and a matched control
without chlorine loses its chlorine-free candidates; the count of
`n_isotope_formula_impossible_dropped` in the pool summary stops being zero.

## Stage 4 — the halogen fragment filter

`vendor/nce/elucidation/ms2Ion.py:115-118` discards every fragment formula
containing Cl or Br unless `iso_count["[Cl37-1]"]` or `iso_count["[Br81-1]"]` is
non-zero. The producer writes those counts under the bare names `"Cl37"` and
`"Br81"` (`ms1Analyzer.py:280,293`), and `iso_count` is a `defaultdict(int)`, so
the bracketed lookups are unconditionally zero and the filter always fires.

Change the two lookups to the bare keys. Add a contract test asserting that the
keys `analyze_isotopes` writes are the keys `is_formula_isotopically_ok` and
`ms2Ion` read — the class of bug is a name agreement, so test the agreement rather
than the behaviour.

**Constraint:** this is vendored code that cannot run here. Ship it as a fix with
the contract test and a note in the commit that the behaviour change is unverified
in-repo, and flag it to whoever owns the NCE application. Expect the fix to make
halogenated fragment formulas appear where none did, which will change MS2 scores
on halogen-bearing features.

## Stage 5 — the formula rules that are missing

Lowest priority, because unlike stages 1 to 4 nothing here is *wrong* today; it is
absent. Do it as measurement first.

- **Senior's three rules** in `structural_elucidation/chemistry/formula.py`: the
  valence sum must be even, at least twice the maximum valence, and at least
  `2 * (atoms - 1)`. FML-3's integrality test is equivalent to the first; the other
  two are not implemented and are cheap.
- **Reconcile the two DBE definitions.** `chemFacts.dbe` uses maximum valences and
  includes P and S; the portable `formula_harmony_score` uses
  `C - H/2 + N/2 + 1 - hal/2` and omits both. They disagree on every phosphate and
  sulfate, which is a large fraction of this matrix. Pick one, and say which in
  `docs/identification_rules.md`.
- **A hydrogen-count bound.** The Kind-Fiehn hydrogen rule, or a defensible
  substitute fitted to the reference library, which is a better source for this
  matrix than a published table.

**Measure before gating.** Run each as a *label* over the delivered candidate set
first and report how many candidates it would reject and how many of those are the
truth structure. A rule that rejects one truth structure per hundred rejections is
not worth turning on. The precedent is `tools/audit_thresholds.py`, which swept a
cutoff and found the curve flat.

## Stage 6 — say it in the report

Once stage 3 lands, a feature's isotope evidence is a fact about the compound that
a reader should see, and at MSI Level 4 the formula is the whole claim.

- An evidence line naming the elements the isotope pattern requires, and the count
  where ISO-2 supplies one.
- At Level 4 and 5, state the halogen constraint alongside the formula: "the M+2
  pattern requires one chlorine" is a stronger statement to a chemist than the
  formula alone.
- State the negative case too, per HAL-2: fluorine and iodine are monoisotopic and
  cannot be evidenced, so a candidate naming either is asserting it from mass and
  model. A report that names a fluorinated structure should say so.

Follow the disclosure rules in `tests/test_report_disclosure.py`; do not leak
fragment detail into the public bundle.

- `linear_mass_match_score` and `predict.mass_match_score`. Owned by the

- The Platt constants, until stage 1 is decided. Refit once, at the end, not per

## Unresolved questions

- **Is the CHRO_LIB exporter fixable at source?** If it is, stage 1's in-repo
  repair is a stopgap and should be marked as one. If it is not, the repair is
  permanent and belongs behind a stable interface rather than inline in
  `mass_hypotheses`.
- **What does `m-H+62.9959` assert?** Either the feature *is* that ion, in which
  case stage 1's derivation is right, or the label is naming an observed buddy
  peak, in which case the feature is plain `m-H` and deriving a shifted mass makes
  it worse. 431 rows and no way to tell from this checkout. Until it is answered,
  exclude the `numeric_offset` family from stage 1's derivation and report it
  separately.
- **What is the uppercase `M+21` convention?** 45 rows, a different labelling
  scheme, and the only rows whose stored mass already differs from `[M±H]` by more
  than 0.01 Da.
- **Floor or window for the isotope hint?** See stage 3. Getting this wrong in the
  permissive direction wastes the evidence; wrong in the strict direction discards
  correct structures.
- **Does a wider target set help?** The whole of stage 1's gate. The honest prior
  is that it is neutral on the 92 truth controls, because 92 controls resolve
  almost nothing — which is the argument in `docs/mass_axis_decisions_needed.md`
  for the library-holdout validation, and the reason to build that first if the
  answer has to be trustworthy.

## How to dispatch this

Stage 0 first and alone; everything imports it.

Then **stages 1+2 and stages 3+4 are independent and can run concurrently**. They
touch different files (`pipeline/candidates.py` and `reports/confidence.py` against
`tools/build_isotope_signals.py` and `vendor/`), and they answer different
questions. Do not merge either into the other's branch before both are measured;
stage 1 changes neutral masses and stage 3 changes which candidates survive, and a
combined result is not attributable to either.

Stage 5 is measurement-only until its numbers come back, so it can run at any
point. Stage 6 is gated on stage 3 landing.

Stage 2b is the one piece with no dependencies and a known defect behind it. If
only one thing gets done, do that.
